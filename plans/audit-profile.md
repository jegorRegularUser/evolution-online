## 1. DDL: правило auth и фактическое использование

1.1. **Правило `user_id TEXT` соблюдено во всех четырёх таблицах** [подтв. по коду]. `evo_profiles.user_id text primary key` (0012:17), `evo_wallets.user_id text primary key` + FK (0012:28), `evo_cosmetics_owned`/`evo_cosmetics_equipped` — `text not null` + FK (0012:37, 49). snake_case; camelCase-таблицы Better Auth (0001_auth.sql:19–63) не тронуты — 0012 лежит рядом с auth-папкой, не внутри неё.

1.2. **FK-граф корректен и совпадает с тем, как сервис реально пишет** [подтв. по коду]:
- wallets→profiles, owned→profiles, equipped→profiles — все `on delete cascade` (0012:28, 37, 49): удаление профиля чистит всё производное;
- составной FK `equipped(user_id,item_id) → owned(user_id,item_id) on delete cascade` (0012:54) держит инвариант «экипировано только владеемое» на уровне БД; ссылка валидна — PK `(user_id,item_id)` у owned (0012:41) даёт нужный unique-индекс;
- `equipItem` пишет только после select-проверки владения (service.server.ts:206–215) — FK страхует гонку между проверкой и записью (см. 2.6).

1.3. **`check (balance >= 0)` (0012:29) — второй рубеж CAS** [подтв. по коду]: даже запись мимо сервиса не может сделать баланс отрицательным (см. 2.2).

1.4. **Слоты и item_id на уровне БД не ограничены** [подтв. по коду]. `slot` — свободный text (PK `(user_id,slot)`, 0012:53), `item_id` — text; enum слотов (shared.ts:20, 24) и форма item_id (shared.ts:31–36) валидируются только сервисом — для слотов это зафиксировано комментарием 0012:44–45, для формы item_id — комментарием shared.ts:27–29. Следствие: прямой SQL может экипировать произвольный slot/item_id (в пределах владения) — мимо каталога волны 3б. Компромисс осознанный, но записан здесь.

1.5. **Мёртвые колонки волны 0** [подтв. по коду]: `updated_at`/`last_seen_at` у evo_profiles (0012:19–20) пишутся только при создании (service.server.ts:94 — все три поля одним stamp); ни один метод сервиса их не обновляет, `last_seen_at` навсегда равен `created_at`. Не баг, но контракта «кто трогает last_seen» нет — к волне 3а не забыть.

1.6. **Баланс — `integer` (int4)** [гипотеза]: переполнение при суммарных ~2,1 млрд; БД отдаст ошибку (не минус), но она не ProfileError → клиент получит invalidResponse. Требует либо прямого SQL, либо ~215 тыс. максимальных выдач — до волны 3 нереалистично.

## 2. Сервис: границы, CAS, идемпотентность, даты

2.1. **Границы порции симметричны и проверяются до обращения к БД** [подтв. по коду]: grantCoins (service.server.ts:141–151) и spendCoins (:159–172) — `Number.isInteger`, 1..10 000, source после trim 1..32 (:79–85). Тесты: profile.test.ts:81–93.

2.2. **CAS-инвариант «баланс не уходит в минус» держится во всех трёх сценариях из ТЗ** [подтв. по коду + семантика БД; гонка live не воспроизводилась]:
- списание — один оператор `update ... where user_id=$1 and balance >= $2 returning balance` (service.server.ts:164–167). Конкурентные UPDATE одной строки сериализуются блокировкой строки; проигравший в READ COMMITTED повторно вычисляет WHERE на новой версии строки (EvalPlanQual) и получает 0 строк → `insufficient-funds` (:168–170). Несколько инстансов сервиса поверх одной БД ничего не меняют — инвариант живёт в БД, не в JS-состоянии;
- запрос вне сервиса и прямой SQL — держит check 0012:29 как ограничение (ошибка, не минус).

2.3. **Чего инвариант НЕ держит — фабрикацию баланса вверх** [подтв. по коду]. Check и CAS защищают только нижнюю границу. Любой будущий код с доступом к `getSql()` может написать `update evo_wallets set balance = balance + 1_000_000` — схема этого не запрещает, «все запросы через сервис» (0012:9–11) — соглашение, не механизм. GRANT_MAX ограничивает порцию, но не сумму: N вызовов grantCoins по 10 000 ничем не ограничены, журнала выдач нет (ledger — комментарий service.server.ts:136–139 отдаёт его волне 3а). Сейчас клиентской ручки на начисление нет (3.1), поэтому риск — только от будущих волн. Рекомендация: ledger + правило «начисление только через сервис» проверять код-ревью волны 3а, схемой не закрывается.

2.4. **ensurePlayer не атомарен** [гипотеза — fault injection нет]: два INSERT (профиль, кошелёк) без транзакции (service.server.ts:91–101); падение между ними оставляет профиль без кошелька. Обратное (кошелёк без профиля) исключает FK (0012:28). Прямой вред мягкий: spendCoins по профилю без кошелька честно даст insufficient-funds, следующий ensure достроит кошелёк. Стоит либо обернуть в транзакцию, либо принять и записать.

2.5. **grantItem идемпотентен, в том числе под гонкой** [подтв. по коду]: PK `(user_id,item_id)` + `on conflict do nothing` (service.server.ts:187–190); конкурентные выдачи одного предмета — одна вставит, вторая получит `alreadyOwned:true` без дубля строки (тест :113–122 — только последовательный случай). Семантическая деталь: `source`/`acquired_at` первой выдачи сохраняются навсегда — повторная выдача с другим source молча игнорируется (обновления нет). Для «правило награды не обязано помнить» это желаемое, но волна 3б (магазин, смена source) должна знать.

2.6. **equipItem: TOCTOU между проверкой владения и upsert закрыт FK, но ошибка уходит в общий код** [подтв. по коду для маппинга; сама гонка не воспроизводилась — гипотеза]. select владения (:206–209) и upsert (:213–215) — два statement'а; если владение сняли между ними, insert упадёт по FK (23503), инвариант БД держит — но исключение не ProfileError, и fail() (api.ts:37–43) отдаст клиенту `invalidResponse` вместо `not-owned`. Косметика UX.

2.7. **toIso между pg и PGlite согласован** [подтв. по коду]: timestamptz оба драйвера отдают Date — db.ts перекрывает парсеры только OID 20/1082/1186 (db.ts:65–67, 93–94, 115–119), timestamptz (1184) не тронут; toIso (service.server.ts:67–69) вызывает `toISOString()`. Нюанс: строка прошла бы насквозь без проверки, что она ISO (`typeof value === "string"` → как есть) — контракт ISO гарантируется лишь тем, что строк сейчас не бывает. Проверено только на PGlite (T:19–30); pg/Neon-путь тестом не покрыт (пробел 4.5).

2.8. **Находка: getProfile — не чтение** [подтв. по коду]. Комментарий (:105–107) обещает «без лишних апдейтов», но :110 вызывает ensurePlayer — каждый profileGet выполняет два `insert ... on conflict do nothing` (evo_profiles, evo_wallets). Строку конфликт-ветка не меняет, но это два write-пути за «чтение», на Neon — два лишних round-trip; в связке с отсутствием rate limit (3.3) — усилитель нагрузки. Рекомендация: getProfile без ensurePlayer (пустой кадр при отсутствии строк) либо ensure только на write-путях (grantCoins и equipItem его и так зовут).

## 3. API-поверхность

3.1. **grantCoins/spendCoins/grantItem клиентской ручки не имеют** [подтв. по коду]. В api.ts экспортированы только profileGet (:46–55) и cosmeticsEquip (:58–73); других createServerFn в модуле нет. Grep по src/: имена grant/spend/grantItem встречаются только в service.server.ts, profile.test.ts и в док-комментарии api.ts:7 (само перечисление «чего нет», не код). Сервис с клиента невытягиваем: он не создаёт server functions, а вызов createProfileService в браузере упал бы на getSql() (db.ts:172–178 бросает в window-контексте).

3.2. **authMiddleware реально стоит на обоих вызовах, userId — только из контекста** [подтв. по коду]: profileGet (:47) и cosmeticsEquip (:59) — `.middleware([authMiddleware])`; вход cosmeticsEquip через validator equipInputSchema (:60); клиентский userId нигде не принимается. requireUserId fail-closed при `DATABASE_URL` + auth off (verify.server.ts:84–93), dev-user — только против PGlite; скриптовые кросс-сайтовые запросы отсекает assertSameSiteRequest (middleware.ts:41–44).

3.3. **Находка: rate-лимитов на profileGet/cosmeticsEquip нет** [подтв. по коду — отсутствие]. Сетевой слой лимитирует лобби: вход/наблюдение/реконнект 30/мин на источник (server.ts:164, entryGuard :1215–1225), чат 20/мин + 700 мс gap (:137–138), создание столов 10/час (:171), анти-брутфорс 10 неудач/5 мин (:161–162) — с честной оговоркой «на инстанс» (:157, :1152–1156). Профильный api.ts не ограничивает ничего, а profileGet — write-усиленный (2.8). Потребителей пока нет (grep: ни одного вызова profileGet/cosmeticsEquip вне модуля), но это первый экспортируемый наружу серверный API без лимитов в репо. **Рекомендация (ожидаемый долг волны 3, фиксируется здесь):** скользящее окно в духе rateHits по ключу источник+userId; ориентиры 30–60/мин на profileGet и 10–20/мин на cosmeticsEquip [гипотеза — пороги не замерялись]; лучше общий лимитер на все server functions, чтобы не копировать guard'ы по модулям.

3.4. **Маппинг ошибок** [подтв. по коду]: ProfileError → `{ok:false, error, code}` (api.ts:37–43); всё прочее (Zod-дампы, тексты БД) сворачивается в `invalidResponse` без деталей наружу.

## 5. Совместимость: ленивое применение 0012

5.1. **PGlite — in-memory, «старой базы» между рестартами нет** [подтв. по коду]: инстанс создаётся без dataDir (db.ts:114–120), данные живут в пределах процесса (комментарий db.ts:110–111). Пользователь, обновившийся с прошлой версии: рестарт dev-сервера → свежая база → 0002..0012 применяются по порядку (сортировка localeCompare по basename, migration-plan.mjs:41–45; «0012_» > «0011_» строково) → пустые таблицы профиля.

5.2. **Живой процесс с HMR** [подтв. по коду]: новый инстанс модуля db.ts переприменяет pending — 0012 доприменится к выжившей базе; партии/комнаты не тронуты, профиль пустой и создаётся лениво первым profileGet (ensurePlayer). Что видит пользователь: баланс 0, владение и экипировка пустые — для волны 0 корректно, backfill не нужен.

5.3. **Neon** [подтв. по коду]: 0012 применяется при сборке (scripts/migrate.mjs, readdir нерекурсивен — :9–10); записи `_migrations` keyed по basename (migration-plan.mjs:20–22) не дадут повторов; существующие пользователи получают профиль лениво, как в 5.2.

5.4. **Главный compat-вывод** [подтв. по коду]: на проде (`DATABASE_URL`) с выключенным auth весь профильный API падает fail-closed (verify.server.ts:21–27, 86–91; api.ts:12–15 фиксирует это честно). До включения auth волна 0 существует только на PGlite — осознанное решение коммита, но в волну 3а «включение auth» должно входить обязательным шагом, иначе магазин накатывается на мёртвый фундамент.

5.5. **Расхождение в шапке 0001_auth.sql** [подтв. по коду]: её комментарий (:9–11) обещает автоприменение auth-схемы и на PGLite при старте, фактически оба аплайера нерекурсивны и auth-папку пропускают (migration-plan.mjs:11–13, db.ts:140, migrate.mjs:9–10) [гипотеза: комментарий — boilerplate CLI]. Включение auth требует копирования 0001_auth.sql в migrations/ (процедура описана там же); конфликт имён исключён keying'ом по basename.
